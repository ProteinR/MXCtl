## Как мерили

MacBook на Apple Silicon + внешний монитор 2560×1440 75 Гц, macOS 26. Сборка `PROFILE=1
scripts/install.sh` (подпись с get-task-allow для `leaks`, `heap`, `xctrace`). «До» — архив HEAD
(0.1.14), собранный так же и запущенный из своей папки, с теми же разрешениями.

```bash
python3 scripts/profile.py 60 "idle" MXCtl                       # покой
python3 scripts/profile.py 30 "wheel" MXCtl                      # вместе с генератором колеса
open -a ~/Applications/MXCtl.app --args --stress-test            # 3 круга: все 6 страниц настроек и панель ×10
open -a ~/Applications/MXCtl.app --args --panel-test             # панель ×6, самый долгий кадр
open -a ~/Applications/MXCtl.app --args --settings-scroll-test   # список кнопок (раскрыт), 10 с
open -a ~/Applications/MXCtl.app --args --settings-scroll-test battery
~/Applications/MXCtl.app/Contents/MacOS/MXCtl --open-settings battery & sleep 7; footprint -p $(pgrep -x MXCtl) | grep phys_
leaks $(pgrep -x MXCtl); heap $(pgrep -x MXCtl)
```

Стресс-тест пишет в лог для каждой страницы время открытия и память через 1 с, а после каждого
круга — память. Пик за весь прогон — `phys_footprint_peak` у `footprint`.

Генератор колеса (вне репозитория, `swiftc -O wheel.swift`). Он посылает щелчки колеса всей
системе: их перехватывает плавная прокрутка MXCtl (это и меряется), а прокручивается окно под
указателем — запускать, когда за Mac никто не работает. `--settings-scroll-test` событий не
посылает: он сам двигает список в окне настроек MXCtl.

```swift
import CoreGraphics
import Foundation
let end = Date().addingTimeInterval(30)
var direction: Int32 = 1
while Date() < end {
    for _ in 0..<6 {
        CGEvent(scrollWheelEvent2Source: nil, units: .line, wheelCount: 1, wheel1: direction, wheel2: 0, wheel3: 0)?.post(tap: .cghidEventTap)
        usleep(60_000)
    }
    direction = -direction
    usleep(400_000)
}
```

Журнал за год — синтетический файл вместо `events.jsonl` (настоящий сохранить и вернуть вместе со
строками, дописанными за время теста). Строки — в формате приложения (`{"kind":"…","time":"…"}`,
без пробелов): по нему журнал отсеивает ненужные строки, не декодируя их.

## Второй заход (0.1.16, 20 октября 2026)

- **Пик ~100 МБ графической памяти на страницах настроек.** В footprint это «Owned physical
  footprint (unmapped) (graphics)»: 93 МБ на 1–2 с, потом 76 МБ становятся «Reclaimable» и
  перестают считаться. Две причины:
  - **Системный переключатель** (`Toggle` в `Form`, «стеклянный» в macOS 26) — то же, что нашёл
    MeetRec. Теперь в настройках свой `LightSwitchStyle` (`LightSwitch.swift`), на вид такой же:
    «Общие» 140 → 54 МБ.
  - **График батареи.** Любой нарисованный Swift Charts давал пик: только оси, только линии,
    с `.drawingGroup()` — всё равно. Пустой график — без пика. SwiftUI `Canvas` вместо Charts —
    тот же пик (хватало одной сетки). Картинка, нарисованная AppKit (`NSImage` с
    `drawingHandler`), — без пика и на ~15 МБ меньше после открытия (41 МБ вместо 55–57). График
    теперь так и рисуется: ступенчатая линия, бледная заливка, сетка, подписи — как было.
    Растровая картинка вместо ленивой ничего не дала, осталась ленивая.
  Нашлось делением страницы «Батарея» (временный флаг, скрывавший части) и замером
  `footprint` через 7 с после открытия.
- **Журнал событий держал весь год.** `events.jsonl` за год — ~37 000 строк при ~100 событиях в
  день; каждая строка декодировалась при запуске на главном потоке (120 мс), все хранились в
  памяти (+11 МБ), а страница «Батарея» при каждой перерисовке перебирала их несколько раз
  (события за сегодня, отключённые устройства, последняя полная зарядка). Теперь:
  - в памяти только замеры заряда за год (~5000) и остальные события за 2 дня; последний замер,
    последняя полная зарядка и последняя подсветка по устройствам — в словарях, без перебора;
  - файл читается в фоне на своей очереди, запись идёт за ним по порядку; события, записанные до
    конца загрузки, добавляются после неё;
  - файл отображается в память (`.alwaysMapped`), а строки, которые не нужны, отсеиваются по
    виду и времени (сравнением текста) без декодирования: при полном чтении и декодировании
    оставалось ~8 МБ освобождённой, но не возвращённой памяти (5 МБ в `MALLOC_LARGE (empty)`);
  - строки старше года вырезаются из файла, только когда их набралось 500: раньше файл
    переписывался при каждом запуске ради одной строки.
- **Стресс-тест** открывает окно настроек на каждой странице (обе картинки «Кнопок», «Батарея»,
  «Прокрутка», «Мышь», «Общие») и пишет время открытия и память каждой. **`--settings-scroll-test`**
  был сломан: «Кнопки» с картинкой помещаются в окно, прокручивать было нечего. Теперь в этом
  режиме список кнопок раскрыт; `--settings-scroll-test battery` листает страницу «Батарея».
- **Проверено, исправлять нечего:**
  - таймеры: заряд и подсветка раз в 10 мин, сводка отчётов HID раз в минуту (только в лог и
    только когда отчёты были), опрос разрешений раз в 2 с — только пока их нет. Пробуждений в
    покое 0.0–0.1 в секунду;
  - после пробуждения (лог 20.10, 09:42) каждое устройство настраивается один раз; клавиатура
    отвечает с третьей попытки (через 3 и 10 с), настройки не пересекаются;
  - `heap`: блоки по 352 КБ (20–36 шт.) — кэш преобразования цвета ColorSync
    (`CMMParaCurveTag::MakeTRC`) при рисовании текста, системный.

## Что осталось (не ошибки)

- **Прокрутка страницы «Батарея» подёргивается** (64–103 мс, при прокрутке HEAD 108–111 мс).
  Время уходит в раскладку строк `Form` SwiftUI (`GroupedFormRowLayout`, размеры текста,
  сегментный переключатель), `body` при этом не вычисляется; без графиков то же. Список кнопок
  (`ScrollView`, не `Form`) листается ровно. Исправлять — переделывать страницу из `Form` в
  `ScrollView`.
- После первого открытия настроек или панели остаётся ~38–40 МБ (было 45–48): кэши AppKit и
  SwiftUI, за три круга не растёт. Сразу после запуска — 25 МБ.
